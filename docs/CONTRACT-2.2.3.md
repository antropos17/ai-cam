## Интент (из `docs/PLAN.md` Block 2.2.3, внесён 2026-08-04)

Источником начального состояния поиска становится **снимок живой Play
Mode-сессии** вместо захвата edit-mode-сцены. Пользователь запускает игру,
доигрывает до интересного момента, жмёт «снимок» — BugCam берёт текущее
физическое состояние (позиция, вращение, линейная скорость, угловая скорость,
sleeping — ровно поля существующего stride-14 рекордера,
`StateRecorder.WriteBody`, `Assets/BugCam/Core/StateRecorder.cs:78-104`) как
начальное состояние поиска дивергенции в быстрой локальной PhysicsScene.

## Центральный вопрос: инвариант П.6 контракта 2.2.2 — предлагаемое разрешение

Инвариант П.6 (`CONTRACT-2.2.2.md`, Поправка 2026-08-04, п. 6): «ни один путь
запуска не входит в симуляцию, минуя захватную edit-mode-точку» — полный
`contentHash` вычислим только в edit mode ДО входа в Play Mode (эмпирика
2026-08-04: геометрия меша с выключенным Read/Write в Play Mode нечитаема).
Живой снимок по определению происходит ПОСЛЕ входа в Play Mode. Конфликт
разрешается так (предложение; адъюдикация — вопрос №1):

**Снимок не является захватом.** Снимок записывает ТОЛЬКО состояние
(stride-14 на тело + позы статики + сверочные скаляры) и НИКОГДА — геометрию,
меш-ссылки или структуру сцены. Авторитетный захват (геометрия, meshRef,
полный contentHash, структурный отпечаток) выполняется там же, где сегодня:
в edit mode, внутри `GhostEvidencePlayModeHost.StartTowerSearch`, ДО
переключения `EditorApplication.isPlaying`
(`Assets/BugCam/Editor/GhostEvidencePlayModeHost.cs:101-134`), после того как
пользователь вышел из игровой сессии. Снимок инъецируется в результат этого
захвата как замена начального состояния. Отсюда точные ответы:

1. **Где происходит меш-резолв на снапшот-пути:** в захватной
   edit-mode-точке запуска поиска — бит-в-бит тот же путь, что у scene-рана
   2.2.2 (`SceneCapture.Capture` → `SceneCaptureHandover.Store`,
   `GhostEvidencePlayModeHost.cs:112-122`). Снапшот-путь не добавляет ни
   одной новой точки меш-резолва.
2. **С чем сравнивается симуляционный структурный отпечаток:** с
   `SimulationMeshReference` (vertexCount, subMeshCount, bounds), записанным
   ЭТИМ edit-mode-захватом и переданным раннеру через `SceneCaptureHandover`
   (`Assets/BugCam/Editor/SceneCaptureHandover.cs`);
   `SimulationHarness.ResolveMeshForSimulation`
   (`Assets/BugCam/Core/SimulationHarness.cs:707-765`) не меняется ни в одной
   строке. Инвариант П.6 сохраняется дословно, без поправок.
3. **Тело живой сессии без пары в edit-mode-захвате** (runtime-spawned):
   fail-closed на точке запуска с именованной verbatim-причиной и кодом
   ошибки снапшот-пути (таблица отказов, строка 6; вопросы №2 и №5).

**Отвергнутая альтернатива** (фиксируется, чтобы не пере-открывать): поиск
изнутри той же Play Mode-сессии без выхода в edit mode. Отвергается, потому
что (а) полный contentHash в Play Mode невычислим — пришлось бы ослаблять
капсулу до структурной сверки, ровно того, что П.6 запрещает, и что капсула
2.2.2 честно называет слепой зоной; (б) сегодняшний код уже закрывает этот
путь: запуск scene-рана при `EditorApplication.isPlaying == true` очищает
handover (`GhostEvidencePlayModeHost.cs:112-122`, ветка else →
`SceneCaptureHandover.Clear()`), и раннер падает fail-closed с
`SCENE_MESH_RESOLVE_FAILED` — это закреплённое поведение, а не случайность;
(в) хост гасит только ту Play Mode-сессию, которую сам начал
(`GhostEvidencePlayModeHost.cs:131-133`) — поиск внутри пользовательской
сессии сломал бы и этот ратифицированный контракт окна.

## Поток запуска (снапшот-путь, пошагово)

1. Пользователь входит в Play Mode сам (хост не участвует; ключ
   `EnteredPlayModeKey` не ставится — сессия пользовательская).
2. Пользователь жмёт «снимок» в окне. Снимок пишется в SessionState-handover
   (см. «Снимок»); окно показывает отчёт снимка. Игра продолжается — снимок
   её не останавливает.
3. Пользователь выходит из Play Mode сам.
4. Пользователь запускает поиск (окно/меню → `TryStartTowerSearch`).
   В edit mode, до `isPlaying = true`, выполняется авторитетный захват
   активной сцены — тот же вызов, что у scene-рана 2.2.2.
5. Сопоставление снимка с захватом (см. «Сопоставление и инъекция»);
   несовпадение = fail-closed, поиск не стартует, Play Mode не включается.
6. Успех: определения тел получают состояние из снимка; хэш захвата
   вычисляется по инъецированным определениям (вопрос №6); handover несёт
   уже инъецированный результат; дальше — существующий путь 2.2.2 без
   изменений (Play Mode → раннер → `SimulationHarness.Run`).

## Снимок: поля, момент, атомарность, персистентность

- **Поля на динамическое тело — ровно stride-14 и ничего больше:**
  `rigidbody.position` (3), `rigidbody.rotation` (4), `rigidbody.linearVelocity`
  (3), `rigidbody.angularVelocity` (3), `rigidbody.IsSleeping()` (1) — тот же
  набор и порядок, что пишет `StateRecorder.WriteBody`
  (`StateRecorder.cs:88-103`) и читает `StateRecorder.WriteRigidbodies`
  (`StateRecorder.cs:106-134`). Чтение — через Rigidbody-API, НЕ через
  `transform`: при включённой интерполяции transform внутри кадра может
  отставать от состояния тела (стандартное поведение Unity; в этом репозитории
  эмпирически НЕ проверено — предпосылка П-4).
- **Дополнительно на тело (только для сверки, в симуляцию не идёт):**
  `rigidbody.mass` и размер/масштаб по формуле существующего захвата — для
  строк дрейфа таблицы отказов.
- **Позы статики и кинематики:** снимок записывает мировые position/rotation
  всех статик-кандидатов (включая кинематические тела, замораживаемые в
  статику правилом A2) по их существующим ключам — предложение №3 берёт эти
  позы в симуляцию («результат скриптов становится начальным состоянием»
  распространяется на кинематические платформы).
- **Момент снимка:** один синхронный проход по всем телам в одном
  main-thread-колбэке редактора. Физика игровой сцены шагает только в
  player loop на том же потоке, поэтому проход атомарен относительно
  физического шага: снимок семантически равен «состояние после последнего
  завершённого физического шага N, до шага N+1». Пауза редактора НЕ
  обязательна (вопрос №10). В метаданные снимка пишутся `Time.frameCount` и
  `Time.fixedTime` на момент снимка (информационно; wall-clock не участвует).
- **Персистентность:** JsonUtility-DTO в SessionState — тот же механизм и та
  же планка, что `SceneCaptureHandover` (бит-точность float закреплена пином
  `SceneCaptureHandoverRoundTripsBitIdentically`,
  `SceneCaptureHandover.cs:14`); снимок обязан пережить domain reload входа
  в Play Mode на шаге 6 потока. Для снапшот-handover — свой аналогичный
  бит-точность-пин (обязательный тест).

## Сопоставление и инъекция

Сопоставление снимка с edit-mode-захватом — по существующей схеме stable ID
(hierarchy path + sibling index; ключи статики — текущая схема `#NN`/`#rb`,
`SceneCapture.cs:597-602`). Правила:

- Множества динамик и статик обязаны совпасть **в обе стороны и точно**:
  тело/статика из снимка без пары в захвате И тело/статика из захвата без
  пары в снимке — fail-closed (строки 6, 7, 10 таблицы). Runtime-spawned
  объект, сдвинувший sibling-индексы существующих объектов, ломает ключи
  МНОГИХ записей — это тоже честный fail-closed по несовпадению множеств,
  катастрофический, но безопасный (аргументация — вопрос №2).
- `mass` и размер тела сверяются снимок↔захват; дрейф = fail-closed
  (строки 8, 9). Остальные Rigidbody-параметры не сверяются: захват уже
  fail-closed'ит любые нестандартные значения своими существующими правилами
  (damping, constraints, Discrete, авто-COM/инерция — правила A2/2.2.2 без
  изменений).
- **Инъекция при успехе:** в `SimulationBodyDefinition` каждого тела
  подставляются из снимка `Position`, `Rotation`, `InitialLinearVelocity`
  плюс новые аддитивные поля `InitialAngularVelocity` и `StartsAsleep`
  (вопрос №4); в `SimulationStaticColliderDefinition` — позы из снимка
  (вопрос №3). Геометрия, meshRef, contentHash, отпечаток, `Size`, `Mass`,
  `FullScale`, `Shape` — только из захвата, из снимка НИКОГДА.
- Возмущение применяется к инъецированной позиции цели тем же кодом, что
  сегодня (`SimulationHarness.CreateBody`, `SimulationHarness.cs:796-801`);
  выбор цели — существующий dropdown по телам захвата (display-name
  provider, решение №3 контракта A1).

## Новые каналы начального состояния (аддитивная поверхность Core)

Сквозной канал линейной скорости уже существует: захват читает
`rigidbody.linearVelocity` (`SceneCapture.cs:653`) → 
`SimulationBodyDefinition.InitialLinearVelocity` (`SimulationHarness.cs:178`)
→ `CreateBody` присваивает `rigidbody.linearVelocity`
(`SimulationHarness.cs:831`). Отсутствуют и добавляются аддитивно (новый
хвостовой конструктор, существующие сигнатуры verbatim — правило пинов A1/2.2.2):

1. **`InitialAngularVelocity`** — `CreateBody` присваивает
   `rigidbody.angularVelocity` после линейной скорости. РИСК (эмпирически НЕ
   проверено — предпосылка П-1): дефолтный `Rigidbody.maxAngularVelocity`
   может клампить присвоенное значение; живое тело после удара легко
   превышает дефолтный предел. До измерения контракт НЕ выбирает между
   «поднять maxAngularVelocity до значения снимка» и «fail-closed на
   превышении» (строка 11 таблицы — условная; адъюдикация по данным
   предпосылки).
2. **`StartsAsleep`** — предложение: при `true` `CreateBody` вызывает
   `rigidbody.Sleep()` после присвоения состояния; жизнеспособность —
   предпосылка П-2; альтернатива и откат — вопрос №4. Существующий
   адъюдицированный notice A2 «спит на момент захвата — стартует
   бодрствующим» (`SceneCapture.cs:634-643`) на НЕ-снапшот-путях сохраняется
   без изменений в любом исходе.

`StateRecorder`, `DivergenceEngine`, `EpsilonSearch` — без изменений: stride-14
уже несёт все поля снимка (утверждение PLAN подтверждено кодом,
`StateRecorder.cs:88-103`).

## Хэш захвата — аддитивность (предложение; вопрос №6)

Существующие строки `D|`/`S|` уже несут позицию и линейную скорость
(`SceneCapture.cs:1015-1019`), поэтому инъекция снимка ДО `ComputeHash` даёт
хэш, честно описывающий фактическое начальное состояние симуляции. Правило
аддитивности (прецедент — хвост `|mesh:` 2.2.2):

- На НЕ-снапшот-путях все hash-строки **байт-в-байт прежние** — пины башни
  (`40e46640…` домино, `8b8e9a94…` GateScene222) не сдвигаются по построению.
- Только на снапшот-пути строка `D|` получает хвостовой сегмент с новым
  состоянием: `|state:<angVel "R" invariant>:<sleeping 0|1>`; строка `S|`
  при позах-из-снимка меняется только значениями существующих полей
  (формат строки не меняется).

## Код ошибки (предложение; вопрос №5)

Новый run-level-код **`SNAPSHOT_CAPTURE_FAILED`** для точек «снимок» и
«запуск» снапшот-пути. `SCENE_CAPTURE_FAILED` остаётся за захватом,

инциденты с разными действиями по исправлению.

## Эмпирические предпосылки до кода (обязательные; прецедент 2.2.2)

- **П-1. Кламп угловой скорости:** присвоение `rigidbody.angularVelocity`
  выше дефолтного `maxAngularVelocity` в свежей локальной PhysicsScene —
  переживает ли значение присвоение и первый `Simulate`; измерить фактический
  дефолтный предел. По исходу адъюдицируется строка 11 таблицы либо подъём
  `maxAngularVelocity`.
- **П-2. Перенос сна:** `Rigidbody.Sleep()` сразу после инстанциирования в
  локальной PhysicsScene — остаётся ли тело спящим через N шагов `Simulate`
  до первого контакта; каковы `linearVelocity`/`angularVelocity` спящего тела
  при чтении (снимочная сторона). По исходу адъюдицируется вопрос №4.
- **П-3. Бит-идентичный повтор снапшот-пути:** два поиска от одного
  сохранённого снимка → field-diff metrics/manifest пуст (кроме
  runId/builtUtc) — расширение пина A5 на новый путь.
- **П-4. Rigidbody-API против transform при интерполяции:** чтение
  `rigidbody.position/rotation` в editor-колбэке между кадрами при включённой
  интерполяции тела — совпадает ли с состоянием после последнего шага и
  расходится ли с `transform.position`.
- **П-5. Рантайм-присвоение `Physics.simulationMode`:** не дирти́т ли
  сериализованный `DynamicsManager.asset` и возвращается ли Script в
  следующей сессии (нужно только гейту, не продукту).

## Открытые вопросы для адъюдикации (№1–№10; решения вносятся в текст)

1. **Поток и П.6.** (А) Снимок → выход из Play Mode → стандартный
   edit-mode-захват при запуске (П.6 дословно сохранён; данный черновик).
   (Б) Поиск изнутри живой сессии (требует поправки П.6: симуляция на одной
   структурной сверке без edit-mode-hash). **Рекомендация: А** — Б ослабляет
   капсулу ровно там, где П.6 её защищает, и ломает ратифицированный
   контракт окна «хост гасит только свою сессию».
2. **Runtime-spawned тела.** (А) fail-closed с именованной причиной (строка
   6). (Б) захватывать примитивные (Box/Sphere) спауны прямо в снимке —
   геометрия примитивов читаема в Play Mode. (В) excluded-safely для
   бесконтактных спаунов. **Рекомендация: А** — Б создаёт вторую захватную
   авторитетность и двоит источник хэша; спаун, сдвинувший sibling-индексы,
   всё равно рушит ключи соседей, т.е. Б не спасает типичный случай; В
   маскирует несопоставимость множества. Скоуп-цена честно названа: сцены с
   активным спауном в v0.1 не снимаются.
3. **Позы статики/кинематики.** (А) Позы всех статик-кандидатов — из снимка
   (движущиеся кинематические платформы получают «результат скриптов»;
   данный черновик). (Б) Позы из захвата + бит-сверка со снимком, любой
   сдвиг = fail-closed. **Рекомендация: А** — Б fail-closed'ит каждый проект
   с движущейся платформой, выхолащивая интент блока; Animator-предупреждение
   A2 сохраняется в обоих вариантах.
4. **Сон.** (А) Переносить: `StartsAsleep` → `Rigidbody.Sleep()` (если П-2
   подтверждает жизнеспособность). (Б) Прецедент A2: стартует бодрствующим +
   существующий verbatim-notice (`SceneCapture.cs:640-642`) и на
   снапшот-пути. **Рекомендация: А при зелёной П-2, иначе Б** — PLAN называет
   sleeping частью переносимого состояния; но при неустойчивом Sleep() честнее
   задокументированное пробуждение, чем недетерминированный перенос.
5. **Код ошибки.** (А) Новый `SNAPSHOT_CAPTURE_FAILED`. (Б) Переиспользовать
   `SCENE_CAPTURE_FAILED`. **Рекомендация: А** — прецедент решения №5:
   разные инциденты, разные действия пользователя.
6. **Хэш.** (А) Инъекция ДО `ComputeHash`: хэш описывает фактическое
   начальное состояние; хвост `|state:` только на снапшот-пути. (Б) Хэш по
   захвату (авторские позы) + отдельный snapshotStateHash в секции снимка.
   **Рекомендация: А** — капсула обязана хэшировать то, что реально
   симулировалось; Б оставляет главный хэш описывающим состояние, которого
   в ране не было.
7. **Гейт-сцена.** (А) GateScene222 read-only (данный черновик). (Б)
   DominoScene. (В) новая сцена. **Рекомендация: А** — единственная сцена с
   мешами, т.е. единственная, где гейт доказывает центральное разрешение
   П.6-вопроса; Б не содержит ни одного меша, В противоречит минимализму.
8. **Представление снапшот-рана.** (А) Новое значение
   `GhostSearchSceneKind.SnapshotScene = 2` (аддитивно; int уже
   персистится). (Б) Флаг поверх `CapturedScene`. **Рекомендация: А** —
   значения enum не перенумеровываются (прецедент `SimulationColliderShape`),
   а третий вид рана — семантически третий вид, не модификатор.
9. **Литералы.** Все литералы таблицы и честная строка капсулы — черновик;
   ратификация дословно, по строке (прецедент решения №9 контракта 2.2.2).
10. **Пауза при снимке.** (А) Пауза не обязательна: проход атомарен,
    инстант определён «после шага N». (Б) Требовать `EditorApplication.isPaused`
    до снимка. **Рекомендация: А** — Б добавляет шаг UX без выигрыша в
    детерминизме: атомарность даёт main-thread, а не пауза; кнопка паузы
    остаётся доступной пользователю добровольно.
